# ADR-0023 3단계 방향: 설계 지식 기반과 핵심 로직 분리

- 날짜: 2026-10-03 · 상태: 채택 (방향·문서 양식·규모·파일 형식·저장소 위치: 사용자 선택)

## 맥락
2단계까지의 결론([ADR-0019](0019-semantic-leakage.md), [ADR-0022](0022-threat-model.md)): 가림은 이름을 지키지만 의미는 못 지킨다. 로직의 기밀성은 가림이 아니라 **분리와 라우팅**으로 다뤄야 한다. 그런데
- 무엇이 핵심 로직인지 식별할 **근거**가 없다(사람의 기억에 의존). 근거는 설계서에 있다.
- 실무의 설계서는 수천 줄이라, 통째로 넣으면 일부만 읽히고 나머지는 빠뜨린 채 넘어간다. 로컬 모델(8K)은 더 그렇다.
- 소스코드는 아직 다루지 못한다.

## 결정
1. **설계서를 로컬 지식 기반으로 만든다.** 구성은 결정론이 뼈대, 로컬 LLM은 그 위에 얹는다.
   - 절 트리 + 위치 머리말(조각이 문맥을 잃지 않게 — 컨텍스추얼 RAG의 효과를 LLM 없이)
   - **엔티티 색인**(위키 방식): 용어집 항목마다 그 용어가 나오는 절 전체 목록. 교차 표기(한·일·영)는 용어집이 묶는다.
   - BM25(글자 2개 단위, 별칭 확장). 임베딩과 절 요약 트리는 측정 후 필요하면.
2. **"찾기"와 "빠짐없이 훑기"를 구분한다.** 핵심 로직 식별·제약 수집 같은 작업은 상위 몇 개 검색이 아니라 색인으로 해당 절을 전부 열거해 하나씩 처리한다.
3. **전달 범위 장부**: 어느 절을 읽었고 안 읽었는지 기록해, 읽지 않은 부분에 대한 주장을 기계가 잡는다.
4. 그 지식 기반을 근거로 **핵심 로직 후보를 제안 → 사람이 확정 → 핵심 모듈 본문을 표지판(시그니처·설명)으로 바꾼 사본**에서 클라우드가 비핵심 작업. 테스트는 로컬 원본에서.
5. **실무 상황을 상정한다**: 일본식 수탁개발 상세설계서(정형 양식 반복 + 실무의 지저분함) 약 3천 줄 + 코드 약 5천 줄, 마크다운 변환 상태. 상세는 [docs/scenario-knowledge.md](../scenario-knowledge.md).
6. 같은 저장소의 새 모듈로 만든다(용어집·관문·감사 로그·측정 방법 재사용).

## 이 방향이 푸는 것 / 못 푸는 것
| 2단계의 한계 | 3단계에서 |
|---|---|
| 핵심 식별의 근거 없음 | 설계서 근거로 제안 |
| 소스코드 미지원 | 핵심 모듈 분리 사본 |
| L3가 문서 통째라 거침 | 절 단위로 다룸 |
| 긴 문서를 읽은 척하고 빠뜨림 | 색인 + 전달 범위 장부 |
| 가려도 의미는 샘 | **못 푼다** — 분리해도 "무엇을 하는지"는 드러난다 |
| 관문 우회, 합성 데이터 | 그대로 |
