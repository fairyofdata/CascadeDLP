# 상정 시나리오 — 3단계(D): 설계 지식 기반과 핵심 로직 분리

작성 2026-10-03. 실무도 아니고 실무 규모로 할 수도 없지만, **실무 상황을 상정해서** 만든다. 이 문서는 그 가정을 고정한다.
여기 적힌 프로젝트·회사·사양은 전부 지어낸 것이다. 실제 자료는 쓰지 않는다.

## 1. 상정하는 상황
- 일본 고객사의 업무 시스템을 **수탁개발**하는 팀. 설계서는 일본어, 사내 메모·회의록은 한국어, 코드 식별자·주석은 영어와 일본어가 섞인다.
- 기본 방침은 "고객사 자료 외부 반출 금지"다. 이 시나리오는 그 방침이 **등급제로 운영되는 경우**를 상정한다(가정):
  - 핵심 로직과 고객 식별 정보는 반출 금지 → 로컬 모델만.
  - 그 밖의 일반 구현은 식별 정보를 가린 상태로 승인하에 클라우드 모델 사용 가능.
  - 이 가정이 성립하지 않는 조직(전부 반출 금지)에서는 클라우드 경로를 쓸 수 없고, 로컬 지식 기반 부분만 의미가 있다([ADR-0022](adr/0022-threat-model.md)).
- 자원: RTX 3070 8GB 한 장, 로컬 모델 qwen3.5:9b(컨텍스트 8K). 클라우드는 최상위 모델.

## 2. 상정하는 자료 (합성)
**규모: 설계서 약 3천 줄 + 코드 약 5천 줄.** "몇천 줄 중 앞부분 수백 줄만 읽고 넘어가는" 문제가 재현되는 최소 크기.

| 종류 | 양식 | 분량(목표) |
|---|---|---|
| 基本設計書 | 서술형 (배경·구성·방침) | 약 300줄 |
| 詳細設計書 — 画面定義 | 화면마다 같은 양식 반복: 項目定義 표, イベント処理, 入力チェック, エラー | 8화면, 약 800줄 |
| 詳細設計書 — API定義 | API마다: リクエスト/レスポンス 표, 処理フロー, エラーコード | 15개, 약 900줄 |
| 詳細設計書 — テーブル定義 | 테이블마다 項目 표, インデックス, 備考 | 12개, 약 400줄 |
| 詳細設計書 — バッチ定義·共通処理·外部IF | 일정, 재시도, 에러 코드 체계, 권한 | 약 400줄 |
| 사내 메모 (한국어) | 회의록, 설계 검토 코멘트, 변경 요청 | 약 200줄 |
| 코드 | 모듈 10개 안팎, 대부분 CRUD·연결 코드, **핵심 로직 모듈 2–3개**, 테스트 | 약 5천 줄 |

- 원본은 엑셀·워드지만 **마크다운으로 변환된 상태**를 가정한다. 변환(표 병합·그림·방안지 양식)은 별개의 문제라 범위에서 뺀다.
- 일부러 넣는 **실무의 지저분함**: 改訂履歴와 판 불일치(화면 정의는 v1.1 기준, API 정의는 v1.2 기준), 같은 사양이 두 곳에 다르게 적힘, 절 번호 건너뜀, "別紙参照"로 다른 문서를 가리킴, 같은 개념의 다른 표기(引当 / 할당 / allocation), 미정(TBD) 항목, 표 안에만 있는 중요한 제약.
- 핵심 로직은 설계서에 **근거 문장**이 있다(예: "本ロジックの詳細は別紙(社外秘)", "특허 출원 예정"). 근거 없이 코드에만 있는 핵심 로직도 하나 둔다(문서로는 못 찾는 경우).

## 3. 상정하는 작업 (평가 과제)
| 과제 | 예 | 실패 모습 |
|---|---|---|
| T1 찾기 | "注文登録API의 재시도 횟수는?" | 틀린 절을 근거로 답함 |
| T2 빠짐없이 훑기 | "引当 처리에 걸린 제약을 전부 모아라" | **있는 제약을 빠뜨리고도 모름** |
| T3 불일치 찾기 | "화면 정의와 API 정의가 어긋나는 곳은?" | 한쪽만 읽고 답함 |
| T4 핵심 로직 식별 | "설계서 근거로 반출 금지 대상 모듈을 제안하라" | 근거 없이 지목하거나 빠뜨림 |
| T5 분리 후 작업 | 핵심 모듈 본문을 숨긴 사본에서 비핵심 수정 과제 수행 | 숨긴 부분 때문에 작업 실패, 또는 숨긴 로직을 추측해 냄 |

## 4. 성공 기준 (측정할 것)
- T1 정답률과 **근거 절의 정확도**.
- T2 **누락률**(빠뜨린 절 수) — 통째 투입·앞부분만·제안 방식 비교.
- 전달 범위 장부: 읽지 않은 절에 대한 주장을 기계가 잡아내는 비율.
- T4 핵심 모듈 식별의 재현율·정밀도(문서 근거가 있는 것 / 없는 것 구분).
- T5 작업 성공률(로컬 테스트 통과)과 숨긴 로직의 유출 정도([ADR-0019](adr/0019-semantic-leakage.md)의 방법).
- 색인 구축 시간, 질문당 시간.

## 5. 알고 가는 한계
- 합성 자료다. 실제 설계서의 양·지저분함·암묵지는 이보다 크다.
- 정형 양식이 뚜렷한 문서를 상정한다. 제목 구조가 무너진 문서에서는 트리 방식이 약해진다.
- 3천 줄은 실무 규모의 일부다. 결과는 "이 방식이 규모에 따라 어떻게 무너지는가"의 첫 지점으로 읽는다.
- 로컬 8B 모델의 판단력이 상한이다.
